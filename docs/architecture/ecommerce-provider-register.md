**Verified: 2026-10-07.** Companion to the [enterprise blueprint](ecommerce-blueprint.md). This register separates public documentation from implementation decisions and merchant-onboarding evidence. Public pages can change or conflict; the account's approved API version and effective merchant agreement govern production integration.

The architecture must persist attempt and provider references before an outbound mutation, query ambiguous outcomes, and deduplicate authenticated callbacks against durable records. Never copy examples that disable TLS verification, log credentials in URLs, or wait indefinitely. Separate pending-transaction reconciliation from matching settlements and bank credits. Treat refund acceptance, refund completion and settlement adjustment as distinct observations.

### Pathao implementation status (2026-10-10)

AARAJ has a Pathao-specific implementation for staff booking, webhook intake, tracking observations, manual reconciliation and customer tracking. The application default is disabled; GitHub Environment configuration selects sandbox or live. API and browser integration tests use deterministic mocks; no real sandbox API request has completed and no shipment has been created. A bounded sandbox token request from the production host timed out after DNS/TLS connection, before receiving an HTTP response. No live request was made. The Pathao-to-AARAJ webhook callback is configured in the Merchant Panel, but no provider-delivered event has been verified. The implementation uses the Merchant API and webhook details supplied by AARAJ as Pathao documentation. Pathao's public [Merchant API access guidance](https://help.pathao.com/integrate-pathao-panel-with-website/) confirms that API access is provisioned from the Developer API option in the Merchant Panel, but does not publish a versioned endpoint contract. Pathao's 2025 [automatic address-mapping announcement](https://pathao.com/bn/blog/api-merchant-auto-address-feature/) documents the full-address approach and says to omit recipient city, zone and area fields.

**Unverified behavior:** the supplied Create Order example serializes `item_weight` as a string, while its parameter table calls the field a float; AARAJ sends a JSON number. The supplied price-plan example similarly quotes `store_id` as a string while its parameter table calls it an integer. The sandbox timeout means AARAJ has not verified provider responses or the accepted wire types. These are source-document discrepancies, not additional Pathao rules.

The detailed, dated record of the Merchant Panel API and webhook material supplied by AARAJ is in [Pathao Courier Merchant API](../integrations/pathao-merchant-api.md). It separates Pathao's documented contract from AARAJ behavior and details not specified in the capture. In particular, the capture does not define Create Order idempotency, rate limits, webhook retry/order/replay behavior, amount units, or account-specific service availability.

The supplied Pathao token flow uses the OAuth resource-owner password grant; AARAJ implements that documented flow on the backend and uses refresh tokens for subsequent requests. A real production client secret appeared in conversation material; treat it as compromised and rotate/reissue it before live use. This is a credential incident response, not a Pathao configuration flag. Do not copy credentials to source, environment examples, logs or support material. The callback URL is configured in Pathao's Merchant Panel and has passed Pathao's displayed integration check; delivery of real order events remains unverified.

**Webhook inbox ownership and retention:** Delivery owns the normalized Pathao webhook inbox. It holds provider-event deduplication, retry, and reconciliation state; it is not the immutable business audit record. No repository requirement establishes indefinite inbox retention as an audit requirement, and the implementation currently has no inbox cleanup job. Before production enablement, the business and legal owners must approve a finite retention period and a deletion or archive rule that accounts for replay needs and any legal holds. Keep operator resolution evidence in the separate append-only audit stream under its own approved retention policy. Do not add an archival subsystem until that policy or measured scale requires one.

**The BD four-tier address model is not universally 1:1 with courier zones.** Keep internal administrative identifiers separate from provider service-area identifiers. Provider/service mappings may be many-to-one or need finer address resolution. Version imported data, preserve booking snapshots and confirm serviceability at booking. Missing or ambiguous mappings need review. Nationwide marketing coverage does not guarantee every administrative area supports every service at a fixed price.

### Geography and AARAJ launch quote policy (2026-10-07)

The versioned launch snapshot is imported from the [Bangladesh National Portal division](https://bangladesh.gov.bd/views/division-list), [district](https://bangladesh.gov.bd/views/district-list/) and [upazila](https://bangladesh.gov.bd/views/upazila-list/) pages. The source date, page references, schema version and source names are preserved with the dataset. Internal IDs are deterministic IDs derived from snapshot records, not government geocodes. The canonical hierarchy is Division → District → Upazila where listed; every district is in the launch footprint, and upazila is optional. Free-form delivery details remain separate from administrative geography. Do not rely on a fixed nationwide row count or scrape these pages on customer requests; review and import a new version when the source needs refreshing.

AARAJ's approved customer-facing launch tariff is `AARAJ_DELIVERY_2026_10_07_V1`: BDT 80 for Dhaka District and BDT 130 for every other supported district, effective 2026-10-07. The API resolves the amount from the canonical district and stores its version/effective date with the quote. It does not call a courier API or copy Pathao's public rates. Courier charges, COD commissions, returns, courier-service tax and negotiated rates remain merchant fulfillment/settlement costs for later phases. The customer quote has no COD surcharge.

Delivery rates has one active three-zone configuration. Saving rates applies them immediately to new quotes; placed orders keep their saved delivery amount. The configuration stores BDT rates for Inside Dhaka, Suburban and Outside Dhaka and uses the official geography snapshot for its area rules. A district rule sets that district's default; an upazila rule overrides it where delivery pricing differs. Locations without a rule use the configured Outside Dhaka rate. Checkout requires an upazila only when the selected district has an upazila-specific rule, so the fee is resolved from the most specific configured official location. Do not infer rates or boundaries from courier tariffs or free-form delivery details. Quote and order snapshots retain the resolved zone, tariff reference, effective date and amount; audit records capture the previous and updated configuration with the operator's reason. This internal history supports quote validation and auditability and is not a scheduled-rate workflow in the admin. The API fails closed when a zone tariff is paired with a different active geography snapshot.

## Social commerce and conversion tracking

The [WhatsApp Business Messaging Policy](https://whatsappbusiness.com/policy/), last updated September 23, 2026 when inspected, requires recipient opt-in and honoring opt-out. Business-initiated conversations use approved templates; free-form replies are allowed within the 24-hour customer-service window, while messages outside it require approved templates. Automated replies need an accessible human escalation route. Persist consent purpose/source/time/version, channel eligibility, template approval and revocation state. Operational necessity does not override WhatsApp channel consent or sending rules; choose an eligible alternate channel when needed.

Meta's [official Messenger Send API collection](https://www.postman.com/meta/messenger-platform-api/folder/7cc3gd2/send-api) describes a standard 24-hour window or an applicable permitted route outside it. Keep Messenger eligibility separate from WhatsApp templates and permissions. Verify current platform permissions and policy exceptions for the deployed API version.

Meta's [maintained server-event source](https://raw.githubusercontent.com/facebook/facebook-nodejs-business-sdk/main/src/objects/serverside/server-event.js) confirms that CAPI event identity uses `event_id` with `event_name`. Generate one stable ID per logical conversion, propagate the corresponding ID to browser/server delivery, preserve it on retries, and use the original occurrence time. Define the purchase milestone explicitly for prepaid and COD orders. Do not emit another purchase for each shipment or repeated payment callback. Marketing consent and data-sharing authorization remain separate from messaging consent; hashed identifiers are still sensitive data.

Direct Meta developer pages returned access/rate-limit errors during this review. Current event-age limits and deduplication receipt-window duration were therefore not verified from accessible primary documentation; pin and test those limits before release. This register does not prescribe a numeric window based on third-party articles.

## Adapter go-live evidence

These are architectural acceptance requirements, not claims that every provider offers every capability. Unsupported capabilities must be represented explicitly and have an approved operational fallback.

| Evidence                  | Required artifact or exercise                                                                                                 | Blocking result                                                  |
| ------------------------- | ----------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------- |
| Account and version       | Merchant approval, approved product/API version, permitted use, sandbox/live separation, credential ownership/rotation record | Guessed endpoint/version or absent production access             |
| Financial representation  | Approved amount/currency mapping and fixtures for subunits, boundaries, malformed values and fee bases                        | Float arithmetic or unverifiable amount/currency                 |
| Authenticity              | Official callback/signature or verification protocol; valid/tampered/replayed fixtures; raw-body handling where specified     | Callback success accepted without trusted verification           |
| Ambiguous payment outcome | Execute/create timeout, delayed success and retry exercise; durable merchant/provider references                              | New charge created while an earlier outcome is unknown           |
| Refund lifecycle          | Capability statement, initiation/query evidence, partial refund and unknown-outcome exercise                                  | Acceptance treated as completion or refundable amount exceeded   |
| Courier booking recovery  | Stable merchant reference, supported query/dedup route, timeout exercise and manual fallback                                  | Duplicate consignment created after an ambiguous response        |
| Geography and quote       | Versioned provider mapping, serviceability fixtures, quote/contract snapshot and unresolved-area route                        | Arbitrary default area or unverified serviceability              |
| Status and reconciliation | Duplicate/out-of-order events, polling recovery, statement/report sample, bank/payout matching                                | Delivery assumed to prove remittance; discrepancies auto-cleared |
| Privacy and resilience    | Redaction tests, restricted payload retention, request deadlines, backoff/rate limits, credential and provider outage drills  | PII/secrets in telemetry or unbounded retry behavior             |
| Social messaging rules   | Channel consent, approved templates and permissions; CAPI event identity fixture                                               | Unsupported compliance claim or ineligible outbound messages     |

Reverify provider contracts, fees, policies and legal rules during implementation and before launch. Preserve dated evidence and fixture versions with each adapter release. Public documentation gaps do not justify inventing APIs or assuming uniform refunds, webhook signatures, status semantics, reporting access or commission bases.
