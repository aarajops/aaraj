# Pathao fulfillment production readiness

**Review date:** 2026-10-29
**Decision:** **NOT READY — code changes are locally testable, provider validation and operator actions remain open.**
**Scope:** AARAJ's Pathao Courier Merchant adapter and its integration boundary. This is a release gate record, not evidence of successful Pathao calls or production state.

## Executive assessment

AARAJ lets staff confirm the customer order, then book it directly with Pathao from the order panel once the parcel is ready. A successful booking is followed by a one-click pickup record in the same panel; it uses Pathao's saved consignment ID and keeps stock reserved until handoff. Customer delivery quotations remain independent of the courier's delivery fee. The configured base URL selects sandbox or live. Pathao requires a delivery type for booking; AARAJ sends the documented Normal Delivery code `48` as a fixed policy, with no delivery-type environment setting. Tracking stays webhook-first; no polling feature or polling configuration is included.

The integration remains unqualified. The recorded sandbox token request received HTTP/2 `522` from Cloudflare, and no Pathao token response, store list, or booking was obtained; local tests use a mock provider. The supplied Merchant Panel capture requires OAuth password grant, while [RFC 9700 §2.4](https://www.rfc-editor.org/rfc/rfc9700.html#section-2.4) says this grant MUST NOT be used. The exact Pathao product and credentials for AARAJ's merchant account are not verified. Cancellation after a courier booking, return inventory handling, and courier COD remittance reconciliation are not implemented. No production deployment or live booking was performed.

### What the official sources mean for AARAJ

The supplied API document makes `delivery_type` a required integer and defines `48` as Normal Delivery and `12` as On-Demand. Pathao's current Merchant Panel describes standard/nationwide service and its faster Dhaka On-Demand option; AARAJ therefore uses `48` for its regular nationwide orders. The document's Create Order example serializes `item_weight` as a string although its field table says float and its Price Plan example uses a number; AARAJ sends a JSON number. It defines `amount_to_collect` as an integer payable by the recipient, and AARAJ uses the Order's immutable COD amount. Wire acceptance and account-specific behavior remain unconfirmed because the recorded sandbox request received an HTTP/2 `522` from Cloudflare rather than an API response.

Pathao's official address update directly supports the current full-address payload and omission of `recipient_city`, `recipient_zone`, and `recipient_area`. The same example includes `special_instruction`, so AARAJ forwards the customer's normalized instruction. The supplied capture gives no length limit, and AARAJ does not impose a Pathao-specific cap.

Pathao's public website integration help is only a pointer to the Merchant Panel. Its newer Commerce Instant Delivery announcement confirms that Pathao now describes another Developer API and webhook surface, but does not say which one is enabled for this merchant. Do not infer product, authentication, endpoints, fee handling, or settlement compatibility across these surfaces.

Pathao's public fee table is useful context for merchant cost review. It is not AARAJ's tariff, a quote for this account, nor a statement proving fees deducted from a particular COD remittance. Keep the customer charge, estimated fee, provider-confirmed fee, collected COD, and settled funds as distinct data if a financial workflow is later approved.

## Configuration and safe operation

### Runtime configuration

| Variable          | Default           | Use and constraint                                                                                                                       |
| ----------------- | ----------------- | ---------------------------------------------------------------------------------------------------------------------------------------- |
| `PATHAO_BASE_URL` | unset in examples | Must equal the documented sandbox or live URL; this selects the provider environment. The deployed value is not verified by this review. |

The production release workflow passes the selected base URL and matching merchant credentials into the root-owned configuration helper. The booking code uses Pathao's documented Normal Delivery type `48`. No workflow, host configuration, or migration was run against production.

### Credential rotation after confirmed exposure

1. Confirm which credential and environment were exposed from an approved incident record. The sandbox/test credentials shown in public Pathao integration material are not evidence that AARAJ's production credentials were exposed.
2. If a production credential was confirmed exposed, an authorized Pathao account owner revokes that specific credential in the correct merchant product/account and issues a replacement. Rotate related usernames, passwords, or tokens only if the incident record shows they were exposed too.
3. Replace only the confirmed affected credential in the protected GitHub Environment Secret. Do not put it in a commit, issue, shell command, chat, or this runbook.
4. Apply the protected configuration using the existing release process, then restart/reload the API so in-memory settings match.
5. Verify the affected credential set and base URL with the authorized Pathao owner and deployment operator. Do not create a live booking merely to prove credentials work.
6. Record who rotated it, date/time, credential identifier/version (not value), and verification result in the approved incident record. If a token may have been exposed, Pathao's supplied capture does not state revocation semantics; confirm those with Pathao.

### Booking timeout or unknown result

1. Leave the booking claim in its unknown/reconciliation state. Do not submit another Create Order request for the same order.
2. Use the staff Pathao issue/booking view and inspect the provider panel or supported order-info route for the merchant order reference/consignment.
3. If a consignment is found, have authorized staff record its exact consignment ID and evidence through the existing idempotent manual reconciliation flow.
4. If no consignment is found, retain the hold and obtain provider/operator evidence before resolving. Lack of a result is not proof the first request failed.
5. Escalate any provider status that conflicts with AARAJ's physical dispatch record. Do not mark dispatched or collect COD from a booking response.

### Missed tracking callback or provider outage

Pathao webhooks are the only automatic tracking update path. If staff see a newer status in the merchant panel than AARAJ shows, record the discrepancy in the approved operations case log and contact the Pathao account operator/support to confirm whether the event can be resent. AARAJ currently has no manual tracking-status override; leave its last accepted event intact until a valid callback is received. Do not edit the database or mark an order delivered based only on a panel screenshot. Booking reconciliation for an unknown Create Order outcome remains a separate, supported workflow.

### Cancellation, returns, and COD settlement

There is no verified Pathao cancellation operation in the capture, and no AARAJ cancellation reconciliation that can safely release a booking claim. Until that workflow exists, use this containment procedure:

1. Before a booking claim exists, use the normal AARAJ order cancellation flow and its inventory rules.
2. While booking is submitting or its outcome is unknown, keep the order and reservation held. Do not issue a second Create Order request. Reconcile by merchant reference or consignment using the provider panel/support and existing AARAJ issue workflow.
3. After a consignment is confirmed, ask the authorized Pathao account operator whether the panel supports cancellation for its current milestone. If it does, follow that account procedure and retain the case/reference and explicit provider confirmation in the approved operations record.
4. Keep AARAJ's booking claim and reservation unchanged even after a provider-side cancellation. The current admin workflow has no audited action to record that cancellation and release stock safely; escalate to the fulfillment owner for an approved application workflow. Do not edit the database or treat a screenshot/status without confirmation as permission to release inventory.
5. For a return, wait for physical receipt and inspection. A provider return event alone does not make goods sellable; use the existing audited inventory adjustment process only after inspection.

This is a safe containment process, not a complete cancellation feature: post-booking cancellation remains blocked in AARAJ and may leave the order/reservation held until a future reviewed workflow is implemented.

Do not equate `order.delivered`, `order.paid`, or the provider's `collected_amount` observation with bank settlement. Reconcile the Pathao statement and bank receipt manually under the business's approved accounting process until a source-backed, auditable ledger/import workflow exists. Never apply the public fee table as a substitute for account transaction evidence.

### Emergency disable and rollback

- To stop new live bookings, switch `PATHAO_BASE_URL` away from the live endpoint or remove the live credentials, apply the host configuration, and restart/reload the API. Existing claims/consignments remain in place and still need reconciliation.
- Preserve manual dispatch and fulfillment. Do not clear credentials, claims, tokens, or reservations directly in the database as an emergency action.

Do not configure the live base URL and credentials until each mandatory qualification has an evidence artifact and an accountable owner.

1. Check the approved incident register for evidence of production credential exposure. Rotate a production credential only if that record identifies it as exposed; no such evidence was established in this review.

3. Resolve the Resource Owner Password Credentials security exception with Pathao and AARAJ security ownership.
4. Run actual sandbox qualification for authentication and refresh, stores, order create/lookup, address/COD/delivery type, webhook authentication and duplicates, timeout recovery, and the account's cancellation/return procedures.
5. Obtain the approved financial statement sample and define COD settlement/courier fee reconciliation. Confirm manual accounting fallback until implementation is approved.
6. Approve webhook inbox retention with business/legal; verify monitoring, stale consignment alerts, provider outage response and staff ownership.
7. Verify API startup, webhook worker, admin authorization, monitoring and manual fulfillment in staging. This scope adds no database migration.
8. Independently verify production GitHub Environment, host runtime, URL/credential pair, ingress/body-size/TLS, restricted DB grants, backups, monitoring and emergency disable procedure. This review did not inspect those live systems.
9. Keep the sandbox base URL configured until the merchant's live product, credentials, Normal Delivery eligibility, and operational handling are confirmed. Verify manual fulfillment and read-only health first.
10. Only after written business authorization, switch to the live base URL and matching credentials for an explicitly approved, low-volume canary. Watch duplicate/unknown bookings, webhook issue backlog, fees and COD discrepancies. Switch back to sandbox and investigate on any safety trigger.
